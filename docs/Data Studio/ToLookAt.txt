• I mean a debugger for the data and model pipeline, not just a debugger for code.

  In CyxWiz, the real user pain is not “my Python line crashed.” It is usually:

  - “why did this dataset turn into the wrong tensor shape?”
  - “where did the NaN appear?”
  - “which preprocessing step changed the labels?”
  - “why does this graph compile but fail at runtime?”
  - “why is the model training, but the outputs are nonsense?”

  A strong visual pipeline debugger would answer those questions by letting the user trace one sample through the whole
  graph.

  What that means in practice:

  - start from one input sample
  - follow it node by node through preprocessing, feature extraction, tokenization, batching, model layers, and output
  - show the actual value at each step, or at least a useful summary
  - show shape, dtype, min/max, mean/std, null counts, token ids, class labels, and anomalies
  - stop exactly where the pipeline first goes wrong
  - let the user click a node and inspect its input/output for that sample
  - highlight the graph path that was actually executed

  So the debugger is not just “logs.” It is an interactive explanation system for the pipeline.

  Why this is important:

  - ML failures are often silent
  - shape mismatches may only appear deep in the pipeline
  - preprocessing bugs are more common than model bugs
  - users often do not know whether the problem is in the data, the graph, or the training loop

  What makes it “best”:

  - It should make the answer obvious in under 30 seconds.
  - A user should not need to inspect raw logs or add print statements.
  - The graph itself should become the diagnostic surface.

  - A text graph tokenizes input, pads it, embeds it, then feeds a classifier.
  - The debugger should show:
      - original text
      - tokens
      - token ids
      - padded length
      - embedding shape
      - layer outputs
      - final prediction
  - If padding breaks, the debugger should show that exact node as the failure point.

  So when I say CyxWiz succeeds if it becomes the best visual pipeline debugger, I mean:

  - it owns the hardest and most annoying part of ML workflow debugging
  - it makes graph-based ML development feel inspectable and trustworthy
  - it gives users a reason to use CyxWiz instead of just coding everything in Python

• Here is a concrete tofix9 feature spec for the Studio Debugger.

  tofix9: Studio Debugger Spec

  Goal
  Build a graph-centric debugger UI inside CyxWiz Engine that explains how one selected sample moves through a pipeline,
  where it changes, and where it fails.

  Primary user

  - ML developer building or debugging a graph in CyxWiz Studio

  Core promise

  - “Select one sample, run it through the graph, see exactly what happened at each node.”

  What it must answer

  - Where did the pipeline fail?
  - What node produced the wrong shape/value?
  - Did preprocessing change the sample unexpectedly?
  - Did the runtime output match the compiler’s expectation?
  - Was the issue data, preprocessing, or model execution?

  Debugger workflow

  1. User opens Studio Debugger
  2. User selects or confirms one sample
  3. User clicks Run Debug
  4. The graph executes in trace mode
  5. The debugger records each node transition
  6. The UI shows the trace timeline, issue summary, and node details
  7. User clicks a trace row to inspect that node
  8. User can jump back to the graph canvas and highlight the node

  Minimum UI

  - Dockable Studio Debugger panel
  - Run button
  - Clear button
  - Session summary area
  - Trace timeline list
  - Selected trace detail pane
  - Issue list
  - Node focus/highlight action
  - Failure state shown inline

  Minimum data shown per trace row

  - Node name
  - Node id
  - Step order
  - Input summary
  - Output summary
  - Shape before / after
  - Execution time
  - Status color
  - Failure marker if applicable

  Minimum data shown in selected trace details

  - Node name and type
  - Input shape
  - Output shape
  - Dtype if available
  - Value summary, not raw tensors by default
  - Duration
  - Validation status
  - Error message if present
  - For text pipelines:
      - original text
      - token list
      - token ids
      - padded length
      - truncation info

  Trace semantics
  The debugger should record these stages when available:

  - input sample acquisition
  - preprocessing
  - tokenization
  - padding / truncation
  - feature extraction
  - model layer execution
  - loss / output stage
  - first failure stage

  Supported issue types

  - Shape mismatch
  - Missing input
  - Invalid dtype
  - NaN detected
  - Inf detected
  - Empty output
  - Compile/runtime mismatch
  - Preprocessing failure
  - Node execution exception

  Graph behavior

  - Trace rows should correspond to actual graph nodes
  - Clicking a row should focus the matching node in the canvas
  - The focused node should be highlighted in CyxWiz Studio
  - If focus fails, the debugger must not crash; it should degrade gracefully

  POC backend contract
  A debugger session should produce:

  - graph hash
  - node count
  - link count
  - sample summary
  - list of issues
  - list of layer/node traces
  - success/failure flag
  - failure summary
  - reached stage

  MVP scope
  Include:

  - one sample
  - one debug run
  - node-by-node trace list
  - selected-node details
  - issue list
  - focus node on click
  - stop on first failure

  Explicit non-goals for the POC

  - multi-sample batch debugging
  - timeline scrubbing
  - breakpoint-style stepping
  - tensor memory viewer
  - session save/load
  - diffing two debug runs
  - live replay of every intermediate tensor element
  - remote debugging

  Text pipeline priority
  Because CyxWiz has strong text and data workflows, the first useful debugger should deeply support:

  - tokenization
  - vocabulary lookup
  - padding
  - truncation
  - text-to-tensor conversion

  Acceptance criteria

  - User can open the debugger from the sidebar
  - User can run a debug session from the debugger panel
  - The panel shows at least one trace entry
  - Clicking a trace entry updates the selected-node details
  - Clicking focus opens/highlights the corresponding node in CyxWiz Studio
  - A failure is shown with a readable message
  - The app does not crash during normal debugger use

  Success metric

  - A user can identify the cause of a pipeline failure in under 30 seconds without adding print statements or opening
    logs.

  Design principle

  - The debugger is not a log viewer.
  - It is an explanation tool for the data-to-model path.
